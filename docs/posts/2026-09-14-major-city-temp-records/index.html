Once a month, pulls each of ~100 major US, Canadian, and Mexican cities’ weather station, tallies how many days in the prior calendar month landed near, at, or beyond that station’s all-time high (and separately, all-time low) for the day, and maps both – plus a running multi-year tally since 2020.

What this page does

Every time this page is rendered (once a month — see the note at the bottom), it:

  1. Takes a fixed list of ~100 cities across the US, Canada, and Mexico (mostly by population, as a standard proxy for “most influential” — see the caveats section for the details and judgment calls involved).
  2. For each city, finds the most complete nearby weather station (the candidate with the longest history and the best coverage of the target month, not just the closest one).
  3. Compares every day of that station’s history against the all-time record for that calendar day — separately for daily highs and daily lows — using an expanding, backward-looking record: a record broken in one year moves the bar for every later year, and never the reverse (see the methodology note and worked example below).
  4. Keeps a running tally since 2020 for both highs and lows, broken out by year.
  5. Focuses on the most recently fully-completed calendar month and, for each city, counts how many days that month landed in each band relative to its record high and its record low — then maps both.
  6. Plots a plain reference map of every city’s location, for anyone who just wants to see where all of them are without any temperature data attached.
Important

This is a live, self-refreshing page, not a one-time snapshot. There’s no server behind it — it’s a static site. At render time, this code re-fetches real station data and recomputes everything below. What you see is only as fresh as the last render (monthly, via cron — see the bottom of the page).

def classify_diff(diff_f, extreme_label):
    """
    Shared classifier for both daily-high and daily-low comparisons.
    diff_f > 0 always means "this day set a new record in the extreme
    direction" -- expanding_daily_comparison() below flips the sign for
    daily lows so this function never has to know which direction it's
    looking at. extreme_label names that direction for the top bucket,
    e.g. "Above" for highs or "Below" for lows.

    The "new record" threshold is diff_f > TIED_BAND_F, not some separate
    number -- it picks up exactly where the "tied" band leaves off, so
    there's no dead zone between "tied" and "record" (an earlier version
    used diff_f > 1 here while TIED_BAND_F was 0.5, leaving diff_f in
    (0.5, 1] classified as neither).
    """
    if diff_f > TIED_BAND_F:
        return f"{extreme_label} record"
    if -TIED_BAND_F <= diff_f <= TIED_BAND_F:
        return "At record (tied)"
    if diff_f >= -3:
        return "Within 3°F of record"
    return None  # not close enough to tally

def classify_month(counts, tiers):
    """
    counts: dict with days_above, days_tied, days_within_3, days_within_10.
    Checked narrowest/most-extreme condition first at each threshold, so
    "3+ days" and "1-2 days" versions of the same band never both match --
    e.g. days_tied=5 satisfies both ">=3" and ">=1", but since ">=3" is
    checked first, it's the one that wins.
    """
    if counts["days_above"] >= 3:
        return tiers[0]
    if counts["days_above"] >= 1:
        return tiers[1]
    if counts["days_tied"] >= 3:
        return tiers[2]
    if counts["days_tied"] >= 1:
        return tiers[3]
    if counts["days_within_3"] >= 3:
        return tiers[4]
    if counts["days_within_3"] >= 1:
        return tiers[5]
    if counts["days_within_10"] >= 3:
        return tiers[6]
    if counts["days_within_10"] >= 1:
        return tiers[7]
    return tiers[8]

def load_koppen_layer():
    """
    Returns (rgba_array, raw_class_codes, (left, right, bottom, top)).
    Class 0 (ocean / no classification, e.g. permanent ice sheets) is left
    fully transparent in rgba so the topography layer underneath shows
    through instead of a solid color standing in for "no data." The raw
    codes are returned too so callers (the legend below) don't need to
    re-open the file just to find out which classes are actually present.
    """
    npz = np.load(KOPPEN_DATA_PATH)
    codes = npz["data"]
    left, bottom, right, top = npz["bounds"]
    rgba = np.zeros((*codes.shape, 4), dtype=np.uint8)
    for code, (_, hex_color) in KOPPEN_COLORS.items():
        r, g, b = (int(hex_color[i:i + 2], 16) for i in (1, 3, 5))
        rgba[codes == code] = (r, g, b, 255)
    return rgba, codes, (left, right, bottom, top)

def resolve_city(label, candidates):
    """
    Among this city's already-fetched candidate stations, pick whichever
    has the most actual years of daily-high history (not just whichever is
    nearest), is recent enough, and covers enough of the target month.
    Station choice is driven entirely by the high-temperature series --
    a station reporting both highs and lows normally has matching coverage
    for both, so this avoids running two separate (and possibly
    conflicting) candidate searches. Returns None (city dropped, reason
    logged) if no candidate qualifies.
    """
    reasons = []
    scored = []
    for station_id in candidates:
        df = station_data.get(station_id)
        if df is None or df.empty or "tmax" not in df.columns:
            reasons.append(f"{station_id}: no data returned")
            continue

        tmax_series = df["tmax"].dropna()
        if tmax_series.empty:
            reasons.append(f"{station_id}: no daily-high data returned")
            continue

        n_years = tmax_series.index.year.nunique()
        if n_years < MIN_RECORD_YEARS:
            reasons.append(f"{station_id}: only {n_years} year(s) of history")
            continue

        latest_available = tmax_series.index.max().date()
        if (TARGET_MONTH_END - latest_available).days > MAX_STALENESS_DAYS:
            reasons.append(
                f"{station_id}: most recent reading ({latest_available}) is more "
                f"than {MAX_STALENESS_DAYS} days before month-end {TARGET_MONTH_END}"
            )
            continue

        coverage = tmax_series.index.normalize().isin(MONTH_DATES).sum() / len(MONTH_DATES)
        if coverage < MIN_MONTH_COVERAGE:
            reasons.append(
                f"{station_id}: only {coverage:.0%} of {TARGET_MONTH_START:%B %Y} covered "
                f"(need {MIN_MONTH_COVERAGE:.0%})"
            )
            continue

        tmin_series = df["tmin"].dropna() if "tmin" in df.columns else pd.Series(dtype=float)
        scored.append((n_years, station_id, tmax_series, tmin_series))

    if not scored:
        raise RuntimeError(f"No usable candidate station for {label}: " + "; ".join(reasons))

    # Most years of high-temp history wins, not nearest distance.
    n_years, station_id, tmax_series, tmin_series = max(scored, key=lambda t: t[0])
    return {
        "station": station_id, "n_years": n_years,
        "tmax_series": tmax_series, "tmin_series": tmin_series,
    }

def expanding_daily_comparison(series, mode="max"):
    """
    For one station's full daily series (highs or lows), return a
    DataFrame (one row per date) with each day's reading compared against
    the expanding, backward-looking record for that calendar day -- i.e.
    the most extreme reading ever seen on that month/day in a *strictly
    earlier* year.

    mode="max" is for daily highs (record = highest prior reading);
    mode="min" is for daily lows (record = lowest prior reading, and the
    sign of diff_f is flipped so that diff_f > 0 always means "this day
    set a new record," regardless of mode -- callers never need to know
    which mode produced a given diff_f.

    Rows where fewer than MIN_PRIOR_SAMPLES earlier years exist for that
    calendar day are dropped, not just rows with zero prior years. A
    station can pass the overall MIN_RECORD_YEARS bar and still have a
    calendar day's "record" resting on only a handful of early
    observations -- comparing against a record that immature makes it
    trivially easy to "beat," which would inflate every tally below with
    noise rather than genuine extremes.
    """
    df = series.rename("actual_f").to_frame()
    df["month"] = df.index.month
    df["day"] = df.index.day
    grouped = df.groupby(["month", "day"])["actual_f"]
    df["prior_n"] = grouped.transform(lambda s: s.expanding().count().shift(1))
    if mode == "max":
        df["prior_record_f"] = grouped.transform(lambda s: s.expanding().max().shift(1))
    else:
        df["prior_record_f"] = grouped.transform(lambda s: s.expanding().min().shift(1))
    df = df[df["prior_n"] >= MIN_PRIOR_SAMPLES]
    if mode == "max":
        df["diff_f"] = (df["actual_f"] - df["prior_record_f"]).round(1)
    else:
        df["diff_f"] = (df["prior_record_f"] - df["actual_f"]).round(1)
    return df[["actual_f", "prior_record_f", "diff_f"]]

The one thing that has to change for a multi-year replay: “the record” can’t be a fixed number looked up once, because it should only reflect what was actually the record at the time — a day in 2021 should be judged against the record as it stood coming into 2021, not against a hotter day that happened to occur in 2023. Method notes & caveats

  • The city list is population plus judgment, not a single strict ranking. Population (~2023-2024 Census-era estimates) is the base proxy for “most influential” — there’s no single agreed-upon ranking for the latter, and population is the one that’s citable and doesn’t change based on opinion — but several rounds of manual additions/swaps followed: Dallas/Fort Worth/Arlington originally plotted three overlapping points in one metro area (trimmed to just Dallas); Oakland, Long Beach, Fresno, Mesa, and Baltimore were swapped for Billings MT, Boise ID, Sioux Falls SD, New Orleans LA, Salt Lake City UT, Birmingham AL, and St. Louis MO for broader geographic spread; a further 25 US cities (mostly state capitals and regionally notable cities named directly) were added, bringing the US total to 75; and Fairbanks AK and San Juan PR were added after that.
  • Canada and Mexico additions, “ignoring suburbs.” Both lists rank by city-proper population (not metro), which is what makes “ignoring suburbs” a real judgment call rather than a simple cutoff: a strict population ranking would include several satellite municipalities that are really just part of a bigger neighbor’s urban area — Mississauga, Brampton, and Surrey (Toronto/Vancouver suburbs in Canada); Ecatepec, Zapopan, and Guadalupe (Mexico City/Guadalajara/Monterrey suburbs in Mexico); and, on reflection, Tijuana’s inclusion was reconsidered and it was dropped too — all excluded even though several individually outrank cities that made the cut. The Canadian list went through several more passes after that: Hamilton, London, Kitchener, and Windsor were removed since, clustered together with Toronto and Ottawa, they made that corner of the map hard to read (even though none of the four is really a suburb in the Mississauga/Brampton sense); Victoria BC, Moncton NB, and St. John’s NL were added specifically to cover provinces that had zero representation otherwise; Gatineau QC was later removed too, once it became clear it was rendering as a second, effectively overlapping point right next to Ottawa at this map’s scale (its own distinct provincial government doesn’t help if the dot is indistinguishable from its neighbor’s); and Charlottetown PE — added for the same provincial- coverage reason as Victoria/Moncton/St. John’s, despite being notably smaller than everything else on the list — was itself later swapped for Kelowna BC. Ranking data for Mexican cities specifically is less precise here than for the US/Canada lists, so the exact cutoff toward the bottom of that list is approximate.
  • City codes. Every city gets a short, unique 2-3 character code, used to label its point on the maps in sections 5 and 8. Most are 3 characters, often that city’s real IATA airport code (ATL, PHX, MIA) — a recognizable 3-letter mnemonic beats a cryptic 2-letter one for most of these cities — though not always: Toronto’s real airport code is YYZ, but TOR reads far more clearly on a map, so a few codes favor clarity over the literal airport code. A handful of especially unambiguous cities (LA, SF, DC, KC, SJ) use 2 characters. The only hard requirement enforced is uniqueness across the whole list.
  • Data source: Meteostat, which aggregates NOAA/NWS (and other) station daily summaries. Station histories vary in length — some (e.g. long-running first-order airports) go back 80+ years; others considerably less. This is each station’s own digitized daily record, not necessarily an official NWS all-time record for that city (which may rely on a longer or differently-sourced period of record).
  • Why monthly, not daily: a single day is a noisy, low-signal snapshot, and daily reruns mostly re-fetched the same station histories for a one-day-later answer. Rendering once a month for the prior, fully completed month gives station data real time to finalize (some long-running stations lag by a week or more — see the staleness note below) and produces a more meaningful “how hot/cold did this month actually run” summary than a single day ever could.
  • Highs and lows share one mechanism, mirrored. expanding_daily_comparison() takes a mode argument (“max” for daily highs, “min” for daily lows) and internally flips the sign of diff_f for the “min” case, so that diff_f > 0 always means “this day set a new record in the extreme direction” regardless of which one is being computed. classify_diff() and classify_month() are likewise shared by both — only the color/label tables (MONTH_TIERS vs. MONTH_TIERS_MIN) and the category names (“Above record” vs. “Below record”) differ.
  • Station choice picks the most complete candidate, not the nearest one. Up to 5 candidates within 120 km are fetched for each city, and whichever has the most actual years of daily-high history is used — not whichever is physically closest. This was a deliberate fix after an initial version picked the nearest station unconditionally (as long as it cleared MIN_RECORD_YEARS), which for at least one test city turned out to be a nearby short/sparsely-reporting site instead of a much longer-running official airport station a few km further out. The same station (and thus the same daily-low series) is used for both the high-temperature and low-temperature analyses, rather than running two independent searches that could disagree.
  • A candidate station must also cover the target month. Beyond overall history length, MIN_MONTH_COVERAGE (80%) requires a candidate to have data for most of the target month specifically — a station can have decades of history and still have gone offline (or not yet reported) for the one month this page currently cares about.
  • Reporting lag / staleness: some stations’ daily summaries aren’t finalized for a couple of weeks. A candidate is rejected if its most recent reading is more than 21 days behind the target month’s end — generous on purpose, since the long-running official stations that make the best record sources also tend to have the slowest final QC lag.
  • A calendar day’s record also needs a minimum sample size of its own (MIN_PRIOR_SAMPLES = 15 earlier years). A station can pass the overall history-length bar while a specific month/day within it still has very few prior observations early in the record, making that day’s “record” trivially easy to beat — this floor keeps those thin spots out of every tally on this page.
  • The multi-year tallies and monthly maps use an expanding, backward-looking record. Comparing every day against the extreme over all years, including ones after it, would let e.g. a hot day in 2024 count as “the record” a 2020 reading is judged against, which reverses cause and effect. Instead, each day is compared only to the most extreme reading ever seen on that calendar day in a strictly earlier year, so a new record set in one year correctly moves the bar for every year after it, and never for years before it — see the worked spot-check in section 3, which finds a real (city, day) example and shows the record baseline actually changing over time rather than just asserting it does.
  • “Tied” means ±0.5°F, not ±1°F. An earlier version of this page used a ±1°F band (diff_f >= -1) for the “tied” tally category, which is a 2°F-wide window, not the 1°F-wide “within a degree” that was actually intended. TIED_BAND_F = 0.5 fixes this: “at record (tied)” now means -0.5 <= diff_f <= 0.5, a 1°F-wide band centered on the record.
  • “Sets a new record” means more than 0.5°F over, not more than 1°F. This threshold should pick up exactly where the tied band leaves off — it was briefly left at the old diff_f > 1 while TIED_BAND_F had already been tightened to 0.5, which left diff_f in (0.5, 1] classified as neither tied nor record-setting. classify_diff() now checks diff_f > TIED_BAND_F instead of a separately hardcoded 1, so the two bands share one boundary with nothing falling between them.
  • Why this color ladder (and why it’s not literally the first draft): it went through a few rounds. The very first version had two buckets defined identically (“< 3 days within 3°F” listed twice). The settled version is a 9-step diverging ladder: two fully-saturated anchor colors at the extremes, shading through progressively lighter tones toward a neutral gray in the middle, with each of the “tied” / “within 3°F” / “within 10°F” bands split into its own “3+ days” and “1-2 days” tier (checked 3+ first, so a city with 3+ days never gets miscounted into the “1-2” tier just because 1-2 is also technically true). One asymmetry worth calling out: the bottom tier’s label (“At least 1 day within 10°F”) is a holdover from before the “3+ days within 10°F” tier existed just above it — in practice that tier only ever fires for 1-2 days now, since 3+ is claimed first, but the exact wording wasn’t revisited.
  • Daily lows use the same ladder shape with the colors deliberately inverted. For daily highs, red means “notably hot” (close to or beyond the record) and blue means “far from the hot record, i.e. a relatively cool month.” For daily lows, blue instead means “notably cold” (close to or beyond the record low) and red means “far from the cold record, i.e. a relatively mild month” — matching the intuitive association of blue with cold and red with warm, at the cost of the two maps not sharing one universal color meaning (check each map’s own legend).
  • Why 2020 for the multi-year tally: 2020 was chosen as a round, recent starting point with enough span to show a year-over-year pattern rather than just one data point; there’s nothing special about that year beyond that.
  • DEBUG_RAISE = False: a city that fails at any stage (no usable station, insufficient history, stale data, insufficient month coverage, or — for the low-temperature analysis specifically — a station that reports highs but not lows) is dropped, with the reason logged as an HTML comment in the page source, rather than taking down the whole page. Flip it to True temporarily to get a full traceback while debugging a specific city.
  • Meteostat’s own per-station-year load failures are logged, not printed to the page. A transient network hiccup fetching one year out of a station’s multi-decade history is something Meteostat already handles gracefully on its own (that year is just dropped; the rest of the fetch continues) – but by default it does so via a stdlib logging.warning(..., exc_info=True) call that, with no handler configured anywhere in this notebook, printed a full traceback straight into the rendered page’s output. logging.getLogger("meteostat").setLevel(logging.ERROR) in the setup cell raises Meteostat’s own log threshold so that noise doesn’t surface, without touching this page’s own failure reporting (run_stage/failures) below.
  • Large-request guard disabled on purpose: Meteostat blocks any single daily-data request spanning more than 30 years by default. That’s turned off here (meteostat.config.block_large_requests = False) deliberately, since computing an honest “record for this calendar day” requires each station’s entire digitized history, not just the last 30 years.
  • Station fetches run in parallel (ThreadPoolExecutor, up to 16 at once) since each is an independent network call to Meteostat’s bulk data. Every candidate for every city is fetched (not just the nearest one, per the station-choice note above), so this stage pulls roughly 5x more station histories than there are cities — still well worth parallelizing, but it’s the long pole in this page’s render time. N_WORKERS was raised from 10 to 16 when the city list doubled from 50 to 100, to keep the total render from simply doubling too; expect somewhere in the 20-30 minute range for all 100 cities. That’s a real cost, but at a monthly cadence it’s a non-issue.
  • Canada and Mexico station coverage is untested territory. Meteostat aggregates station data globally, not just US NOAA/NWS sources, so the same resolve_city logic (longest history, target-month coverage, staleness) is applied to Canadian and Mexican candidates with no special casing. Whether those regions have as many long-running, densely-covered stations within STATION_SEARCH_RADIUS_M as US cities typically do is genuinely unknown until a render actually runs — if a Canadian or Mexican city is missing from a given month’s map, check the HTML source comments for why (same DEBUG_RAISE/failures mechanism as any other city).
  • The main map is deliberately clipped, not a loose “fit everything” extent. MAIN_EXTENT is defined as exactly 1° beyond four named reference points — north of Edmonton, west of San Francisco, east of St. John’s NL, south of Puebla (“Pueblo” as given was read as Puebla, the only spelling used anywhere else in this file; a literal Pueblo, CO reading would cut off all of Mexico, which can’t be right given Mexican cities were being added in the same request). One real consequence: with Puebla itself removed from CITIES in this same round, Oaxaca (added at the same time, ~17.1°N) now sits just south of that clip line and won’t actually show up on the main map, even though it’s still in the city list and still fully tallied — a direct side effect of taking the clip instruction literally rather than quietly padding it out to fit every city that happened to get added alongside it.
  • Alaska and Hawaii get their own insets, positioned inside the map’s own Pacific Ocean space rather than as a separate outside panel — bottom-left, roughly where the ocean west of Mexico/California actually is on this projection. Both are zoomed in tight (Oahu only for Hawaii; the Anchorage/Fairbanks corridor for Alaska) and labeled with just the state name at the top rather than per-city codes, since there isn’t room for a recognizable shape and readable per-city labels at this size. Insets are defined purely by their own geographic extent (a lon/lat box), not a hardcoded city list, so both Alaska cities land in the same inset automatically. Alaska specifically uses its own Lambert Conformal projection centered on Alaska rather than the plain PlateCarree grid — PlateCarree visibly stretches high-latitude land east-west (it doesn’t account for longitude lines converging toward the pole), which was making Alaska look wider than it actually is.

The underlying monthly_df / monthly_df_min tables above each map list every city’s code unambiguously if a label on the map itself is unclear.
  • Section 9’s climate-zone layer is real Köppen-Geiger classification data, not a terrain-shading stand-in. An earlier version of this page used Cartopy’s bundled Natural Earth shaded-relief raster (ax.stock_img()) as a rough visual proxy and was explicit that it was not a genuine climate classification.   • The Köppen data is bundled with the repo, not fetched at render time — a deliberate exception to this site’s usual practice (see the README, and how every other live-data post here fetches fresh each run). The published dataset ships the present-day classification at three resolutions; koppen_na.npz here is the 5-arcmin (“0p083”) grid, cropped once (offline, not at render time) to lon -180 to -50 / lat 14 to 72 and gzip-compressed to 45 KB. That’s a different scale of problem than the multi-GB weather-model output other posts on this site legitimately fetch fresh each run, and unlike a live external fetch, it can’t fail or change format out from under a future scheduled render — worth it here since the classification itself doesn’t change month-to-month the way weather does.
  • Alaska and Hawaii’s insets show the (approximately) full state/territory, not just a tight crop around their cities. ## What this page does

Every time this page is rendered (once a month — see the note at the
bottom), it:

1. Takes a fixed list of **~100 cities** across the US, Canada, and Mexico
   (mostly by population, as a standard proxy for "most influential" — see
   the caveats section for the details and judgment calls involved).
2. For each city, finds the **most complete nearby weather station** (the
   candidate with the longest history and the best coverage of the target
   month, not just the closest one).
3. Compares **every day of that station's history** against the all-time
   record for that calendar day — separately for **daily highs** and
   **daily lows** — using an **expanding, backward-looking record**: a
   record broken in one year moves the bar for every later year, and never
   the reverse (see the methodology note and worked example below).
4. Keeps a **running tally since 2020** for both highs and lows, broken out
   by year.
5. Focuses on the **most recently fully-completed calendar month** and, for
   each city, counts how many days that month landed in each band relative
   to its record high and its record low — then maps both.
6. Plots a plain **reference map** of every city's location, for anyone
   who just wants to see where all of them are without any temperature
   data attached.

**This is a live, self-refreshing page, not a one-time snapshot.** There's
no server behind it — it's a static site. At render time, this code
re-fetches real station data and recomputes everything below. What you see
is only as fresh as the last render (monthly, via cron — see the bottom of

```{python}
def classify_diff(diff_f, extreme_label):
    """
    Shared classifier for both daily-high and daily-low comparisons.
    diff_f > 0 always means "this day set a new record in the extreme
    direction" -- expanding_daily_comparison() below flips the sign for
    daily lows so this function never has to know which direction it's
    looking at. extreme_label names that direction for the top bucket,
    e.g. "Above" for highs or "Below" for lows.

    The "new record" threshold is diff_f > TIED_BAND_F, not some separate
    number -- it picks up exactly where the "tied" band leaves off, so
    there's no dead zone between "tied" and "record" (an earlier version
    used diff_f > 1 here while TIED_BAND_F was 0.5, leaving diff_f in
    (0.5, 1] classified as neither).
    """
    if diff_f > TIED_BAND_F:
        return f"{extreme_label} record"
    if -TIED_BAND_F <= diff_f <= TIED_BAND_F:
        return "At record (tied)"
    if diff_f >= -3:
        return "Within 3°F of record"
    return None  # not close enough to tally

def classify_month(counts, tiers):
    """
    counts: dict with days_above, days_tied, days_within_3, days_within_10.
    Checked narrowest/most-extreme condition first at each threshold, so
    "3+ days" and "1-2 days" versions of the same band never both match --
    e.g. days_tied=5 satisfies both ">=3" and ">=1", but since ">=3" is
    checked first, it's the one that wins.
    """
    if counts["days_above"] >= 3:
        return tiers[0]
    if counts["days_above"] >= 1:
        return tiers[1]
    if counts["days_tied"] >= 3:
        return tiers[2]
    if counts["days_tied"] >= 1:
        return tiers[3]
    if counts["days_within_3"] >= 3:
        return tiers[4]
    if counts["days_within_3"] >= 1:
        return tiers[5]
    if counts["days_within_10"] >= 3:
        return tiers[6]
    if counts["days_within_10"] >= 1:
        return tiers[7]
    return tiers[8]

def load_koppen_layer():
    """
    Returns (rgba_array, raw_class_codes, (left, right, bottom, top)).
    Class 0 (ocean / no classification, e.g. permanent ice sheets) is left
    fully transparent in rgba so the topography layer underneath shows
    through instead of a solid color standing in for "no data." The raw
    codes are returned too so callers (the legend below) don't need to
    re-open the file just to find out which classes are actually present.
    """
    npz = np.load(KOPPEN_DATA_PATH)
    codes = npz["data"]
    left, bottom, right, top = npz["bounds"]
    rgba = np.zeros((*codes.shape, 4), dtype=np.uint8)
    for code, (_, hex_color) in KOPPEN_COLORS.items():
        r, g, b = (int(hex_color[i:i + 2], 16) for i in (1, 3, 5))
        rgba[codes == code] = (r, g, b, 255)
    return rgba, codes, (left, right, bottom, top)

def in_any_inset(df):
    mask = pd.Series(False, index=df.index)
    for spec in INSET_SPECS:
        lon0, lon1, lat0, lat1 = spec["extent"]
        mask |= (df["lon"] >= lon0) & (df["lon"] <= lon1) & (df["lat"] >= lat0) & (df["lat"] <= lat1)
    return mask


def in_main_extent(df):
    """
    A point outside set_extent() doesn't get a marker drawn (scatter
    respects the axes clip box), but annotate() draws its text regardless
    -- so without this filter, a city like Oaxaca that falls just outside
    MAIN_EXTENT (see the caveat where MAIN_EXTENT is defined) would show
    up as a code label floating below the map frame with no dot attached
    to it. Cities excluded here are still fully resolved and tallied
    elsewhere on the page; they just don't get plotted on this map.

    lon0, lon1, lat0, lat1 = MAIN_EXTENT
    return (df["lon"] >= lon0) & (df["lon"] <= lon1) & (df["lat"] >= lat0) & (df["lat"] <= lat1)

def plot_cities(axis, sub_df, show_labels=True, marker_color=None, s=70):
    """
    Scatter each city's point, optionally labeled with its short code
    (offset in fixed screen-space points, not data coordinates, so labels
    stay a legible fixed size regardless of the axes' zoom level).
    marker_color overrides each row's own "Tier color" with one fixed
    color for every point (used by the reference map in section 9, where
    every dot is plain black rather than tier-colored).
    """
    for _, row in sub_df.iterrows():
        axis.scatter(row["lon"], row["lat"], s=s, color=marker_color or row["Tier color"],
                     edgecolors="black", linewidths=0.5, transform=ccrs.PlateCarree(), zorder=5)
        if show_labels:
            axis.annotate(
                row["Code"], xy=(row["lon"], row["lat"]),
                xycoords=ccrs.PlateCarree()._as_mpl_transform(axis),
                xytext=(4, 3), textcoords="offset points", fontsize=6.5, zorder=6,
                bbox=dict(boxstyle="round,pad=0.1", fc="white", ec="none", alpha=0.7),
            )


def draw_insets(fig, df, basemap_fn=add_basemap, marker_color=None, s=70):
    """
    Shared by every map in this post that uses MAIN_EXTENT -- draws the
    Alaska/Hawaii insets defined in INSET_SPECS. basemap_fn lets the plain
    reference map (section 9) reuse this for its own stock_img() terrain
    background instead of the flat add_basemap() the tier-colored maps use,
    without duplicating the inset-layout logic itself.

    for spec in INSET_SPECS:
        lon0, lon1, lat0, lat1 = spec["extent"]
        sub = df[(df["lon"] >= lon0) & (df["lon"] <= lon1) & (df["lat"] >= lat0) & (df["lat"] <= lat1)]

        inset_ax.text(0.5, 0.95, spec["name"], transform=inset_ax.transAxes, ha="center", va="top",

                       bbox=dict(boxstyle="round,pad=0.15", fc="white", ec="none", alpha=0.75))

            spine.set_edgecolor("#333333")
```

## 2. Pull each station's full daily high/low-temperature history

Fetched in parallel — each station's history is an independent network call,
and there's no reason to wait for one before starting the next. Both the
daily high and daily low come back in the same request per station, so
adding the low-temperature analysis below didn't require any extra fetching.

```{python}
#| label: fetch-histories

# Dev-only cache: while iterating on layout/rendering (not on the actual
# station-resolution logic), re-fetching ~250-500 station histories from
# Meteostat on every single test render was by far the slowest part of the
# feedback loop. With USE_LOCAL_CACHE = True, a station already fetched
# once this "session" is loaded from a local pickle instead of re-hit over
# the network -- CACHE_DIR is gitignored and never committed, so this
# changes nothing about what actually ships. MUST be False (the default)
# for the real render that gets pushed, since the cache doesn't know when
# a new month's data becomes available -- it would happily keep serving
# last month's fetch forever otherwise.
USE_LOCAL_CACHE = False
CACHE_DIR = Path("cache_dev")
if USE_LOCAL_CACHE:
    CACHE_DIR.mkdir(exist_ok=True)


def fetch_station_daily(station_id):
    cache_path = CACHE_DIR / f"{station_id}.pkl"
    if USE_LOCAL_CACHE and cache_path.exists():
        return pd.read_pickle(cache_path)
    ts = meteostat.daily(station_id, HIST_START, FETCH_END, parameters=[Parameter.TMAX, Parameter.TMIN])
    df = ts.fetch(units=UnitSystem.IMPERIAL)
    if USE_LOCAL_CACHE and df is not None:
        df.to_pickle(cache_path)
    return df


# Fetch every candidate for every city (not just the nearest one) so the
# best-populated station can be picked rather than just the closest one
# that clears a minimum bar. This matters: nearby() returns candidates by
# *distance*, and the physically closest site is sometimes a short-lived or
# sparsely-reporting station (e.g. a personal/community site) sitting right
# next to a much longer-running official airport station a few km further
# out. Picking "nearest that passes" over "most complete overall" was
# initially producing "records" built on a couple sparse decades instead of
# a station's full, well-populated history.
all_candidate_ids = sorted({sid for ids in city_candidates.values() for sid in ids})
station_data = {}
with ThreadPoolExecutor(max_workers=N_WORKERS) as pool:
    futures = {pool.submit(fetch_station_daily, sid): sid for sid in all_candidate_ids}
    for future in futures:
        sid = futures[future]
        station_data[sid] = run_stage(f"station {sid} (fetch)", future.result)


MONTH_DATES = pd.date_range(TARGET_MONTH_START, TARGET_MONTH_END, freq="D")


def resolve_city(label, candidates):
    """
    Among this city's already-fetched candidate stations, pick whichever
    has the most actual years of daily-high history (not just whichever is
    nearest), is recent enough, and covers enough of the target month.
    Station choice is driven entirely by the high-temperature series --
    a station reporting both highs and lows normally has matching coverage
    for both, so this avoids running two separate (and possibly
    conflicting) candidate searches. Returns None (city dropped, reason
    logged) if no candidate qualifies.
    """
    reasons = []
    scored = []
    for station_id in candidates:
        df = station_data.get(station_id)
        if df is None or df.empty or "tmax" not in df.columns:
            reasons.append(f"{station_id}: no data returned")
            continue

        tmax_series = df["tmax"].dropna()
        if tmax_series.empty:
            reasons.append(f"{station_id}: no daily-high data returned")
            continue

        n_years = tmax_series.index.year.nunique()
        if n_years < MIN_RECORD_YEARS:
            reasons.append(f"{station_id}: only {n_years} year(s) of history")
            continue

        latest_available = tmax_series.index.max().date()
        if (TARGET_MONTH_END - latest_available).days > MAX_STALENESS_DAYS:
            reasons.append(
                f"{station_id}: most recent reading ({latest_available}) is more "
                f"than {MAX_STALENESS_DAYS} days before month-end {TARGET_MONTH_END}"
            )
            continue

        coverage = tmax_series.index.normalize().isin(MONTH_DATES).sum() / len(MONTH_DATES)
        if coverage < MIN_MONTH_COVERAGE:
            reasons.append(
                f"{station_id}: only {coverage:.0%} of {TARGET_MONTH_START:%B %Y} covered "
                f"(need {MIN_MONTH_COVERAGE:.0%})"
            )
            continue

        tmin_series = df["tmin"].dropna() if "tmin" in df.columns else pd.Series(dtype=float)
        scored.append((n_years, station_id, tmax_series, tmin_series))

    if not scored:
        raise RuntimeError(f"No usable candidate station for {label}: " + "; ".join(reasons))

    # Most years of high-temp history wins, not nearest distance.
    n_years, station_id, tmax_series, tmin_series = max(scored, key=lambda t: t[0])
    return {
        "station": station_id, "n_years": n_years,
        "tmax_series": tmax_series, "tmin_series": tmin_series,
    }
```

```{python}
def expanding_daily_comparison(series, mode="max"):
    """
    For one station's full daily series (highs or lows), return a
    DataFrame (one row per date) with each day's reading compared against
    the expanding, backward-looking record for that calendar day -- i.e.
    the most extreme reading ever seen on that month/day in a *strictly
    earlier* year.

    mode="max" is for daily highs (record = highest prior reading);
    mode="min" is for daily lows (record = lowest prior reading, and the
    sign of diff_f is flipped so that diff_f > 0 always means "this day
    set a new record," regardless of mode -- callers never need to know
    which mode produced a given diff_f.

    Rows where fewer than MIN_PRIOR_SAMPLES earlier years exist for that
    calendar day are dropped, not just rows with zero prior years. A
    station can pass the overall MIN_RECORD_YEARS bar and still have a
    calendar day's "record" resting on only a handful of early
    observations -- comparing against a record that immature makes it
    trivially easy to "beat," which would inflate every tally below with
    noise rather than genuine extremes.
    """
    df = series.rename("actual_f").to_frame()
    df["month"] = df.index.month
    df["day"] = df.index.day
    grouped = df.groupby(["month", "day"])["actual_f"]
    df["prior_n"] = grouped.transform(lambda s: s.expanding().count().shift(1))
    if mode == "max":
        df["prior_record_f"] = grouped.transform(lambda s: s.expanding().max().shift(1))
    else:
        df["prior_record_f"] = grouped.transform(lambda s: s.expanding().min().shift(1))
    df = df[df["prior_n"] >= MIN_PRIOR_SAMPLES]
    if mode == "max":
        df["diff_f"] = (df["actual_f"] - df["prior_record_f"]).round(1)
    else:
        df["diff_f"] = (df["prior_record_f"] - df["actual_f"]).round(1)
    return df[["actual_f", "prior_record_f", "diff_f"]]
```

## 3. Back-calculated running tally since 2020 — daily highs

A single month is a small sample — most cities aren't near their record in
any given month. To get a real sense of *how often* major US cities are
running hot relative to their own history, this section replays the
comparison for **every day since `{python} TALLY_START_DATE`** through the
end of the target month, for each of the `{python} len(results)` resolved
cities (using the station histories already pulled above — no extra
fetching needed), and keeps a cumulative tally across all of it. The
per-day results computed here also feed directly into the monthly map in
section 5.

The one thing that has to change for a multi-year replay: "the record"
can't be a fixed number looked up once, because it should only reflect what
was *actually the record at the time* — a day in 2021 should be judged
against the record as it stood coming into 2021, not against a hotter day
that happened to occur in 2023. So for each station and each calendar day,
this uses an **expanding, backward-looking record**: the highest reading
ever seen on that calendar day in any *earlier* year. If a year sets a new
record, that becomes the bar every later year is compared against — and,
just as importantly, a year *never* gets compared against a record set
after it.

```{python}
#| label: historical-tally

daily_frames = []

        continue
    comparison = comparison.loc[TALLY_START_TS:TARGET_MONTH_END_TS].copy()
```

direct check on real data: the (city, calendar day) pair whose "prior
record" baseline changed the *most* times within the tally window above —
concrete proof that when a record is broken, every later comparison for
that same calendar day uses the new, higher number, not the original one.
(The daily-low analysis in section 6 uses the exact same mechanism, just
mirrored to track the lowest prior reading instead of the highest -- this
same evidence applies there too.)

## Method notes & caveats

- **The city list is population plus judgment, not a single strict
  ranking.** Population (~2023-2024 Census-era estimates) is the base proxy
  for "most influential" — there's no single agreed-upon ranking for the
  latter, and population is the one that's citable and doesn't change based
  on opinion — but several rounds of manual additions/swaps followed:
  Dallas/Fort Worth/Arlington originally plotted three overlapping points
  in one metro area (trimmed to just Dallas); Oakland, Long Beach, Fresno,
  Mesa, and Baltimore were swapped for Billings MT, Boise ID, Sioux Falls
  SD, New Orleans LA, Salt Lake City UT, Birmingham AL, and St. Louis MO
  for broader geographic spread; a further 25 US cities (mostly state
  capitals and regionally notable cities named directly) were added,
  bringing the US total to 75; and Fairbanks AK and San Juan PR were added
  after that.
- **Canada and Mexico additions, "ignoring suburbs."** Both lists rank by
  city-*proper* population (not metro), which is what makes "ignoring
  suburbs" a real judgment call rather than a simple cutoff: a strict
  population ranking would include several satellite municipalities that
  are really just part of a bigger neighbor's urban area — Mississauga,
  Brampton, and Surrey (Toronto/Vancouver suburbs in Canada); Ecatepec,
  Zapopan, and Guadalupe (Mexico City/Guadalajara/Monterrey suburbs in
  Mexico); and, on reflection, Tijuana's inclusion was reconsidered and it
  was dropped too — all excluded even though several individually outrank
  cities that made the cut. The Canadian list went through several more
  passes after that: Hamilton, London, Kitchener, and Windsor were removed
  since, clustered together with Toronto and Ottawa, they made that corner
  of the map hard to read (even though none of the four is really a suburb
  in the Mississauga/Brampton sense); Victoria BC, Moncton NB, and
  St. John's NL were added specifically to cover provinces that had zero
  representation otherwise; Gatineau QC was later removed too, once it
  became clear it was rendering as a second, effectively overlapping point
  right next to Ottawa at this map's scale (its own distinct provincial
  government doesn't help if the dot is indistinguishable from its
  neighbor's); and Charlottetown PE — added for the same provincial-
  coverage reason as Victoria/Moncton/St. John's, despite being notably
  smaller than everything else on the list — was itself later swapped for
  Kelowna BC. Ranking data for Mexican cities specifically is less precise
  here than for the US/Canada lists, so the exact cutoff toward the bottom
  of that list is approximate.
- **City codes.** Every city gets a short, unique 2-3 character code, used
  to label its point on the maps in sections 5 and 8. Most are 3
  characters, often that city's real IATA airport code (`ATL`, `PHX`,
  `MIA`) — a recognizable 3-letter mnemonic beats a cryptic 2-letter one
  for most of these cities — though not always: Toronto's real airport
  code is `YYZ`, but `TOR` reads far more clearly on a map, so a few codes
  favor clarity over the literal airport code. A handful of especially
  unambiguous cities (`LA`, `SF`, `DC`, `KC`, `SJ`) use 2 characters. The
  only hard requirement enforced is uniqueness across the whole list.
- **Data source**: [Meteostat](https://meteostat.net/), which aggregates
  NOAA/NWS (and other) station daily summaries. Station histories vary in
  length — some (e.g. long-running first-order airports) go back 80+ years;
  others considerably less. This is each **station's own digitized daily
  record**, not necessarily an official NWS all-time record for that city
  (which may rely on a longer or differently-sourced period of record).
- **Why monthly, not daily**: a single day is a noisy, low-signal snapshot,
  and daily reruns mostly re-fetched the same station histories for a
  one-day-later answer. Rendering once a month for the *prior, fully
  completed* month gives station data real time to finalize (some
  long-running stations lag by a week or more — see the staleness note
  below) and produces a more meaningful "how hot/cold did this month
  actually run" summary than a single day ever could.
- **Highs and lows share one mechanism, mirrored.** `expanding_daily_comparison()`
  takes a `mode` argument ("max" for daily highs, "min" for daily lows) and
  internally flips the sign of `diff_f` for the "min" case, so that
  `diff_f > 0` always means "this day set a new record in the extreme
  direction" regardless of which one is being computed. `classify_diff()`
  and `classify_month()` are likewise shared by both — only the color/label
  tables (`MONTH_TIERS` vs. `MONTH_TIERS_MIN`) and the category names
  ("Above record" vs. "Below record") differ.
- **Station choice picks the most complete candidate, not the nearest one.**
  Up to `{python} N_CANDIDATE_STATIONS` candidates within
  `{python} STATION_SEARCH_RADIUS_M // 1000` km are fetched for each city,
  and whichever has the most actual years of daily-high history is used —
  *not* whichever is physically closest. This was a deliberate fix after an
  initial version picked the nearest station unconditionally (as long as it
  cleared `MIN_RECORD_YEARS`), which for at least one test city turned out
  to be a nearby short/sparsely-reporting site instead of a much
  longer-running official airport station a few km further out. The same
  station (and thus the same daily-low series) is used for both the
  high-temperature and low-temperature analyses, rather than running two
  independent searches that could disagree.
- **A candidate station must also cover the target month.** Beyond overall
  history length, `MIN_MONTH_COVERAGE` (`{python} f"{MIN_MONTH_COVERAGE:.0%}"`)
  requires a candidate to have data for most of the target month specifically
  — a station can have decades of history and still have gone offline (or
  not yet reported) for the one month this page currently cares about.
- **Reporting lag / staleness**: some stations' daily summaries aren't
  finalized for a couple of weeks. A candidate is rejected if its most
  recent reading is more than `{python} MAX_STALENESS_DAYS` days behind the
  target month's end — generous on purpose, since the long-running official
  stations that make the best *record* sources also tend to have the
  slowest final QC lag.
- **A calendar day's record also needs a minimum sample size of its own**
  (`MIN_PRIOR_SAMPLES` = `{python} MIN_PRIOR_SAMPLES` earlier years). A
  station can pass the overall history-length bar while a specific
  month/day within it still has very few prior observations early in the
  record, making that day's "record" trivially easy to beat — this floor
  keeps those thin spots out of every tally on this page.
- **The multi-year tallies and monthly maps use an *expanding*,
  backward-looking record.** Comparing every day against the extreme over
  *all* years, including ones after it, would let e.g. a hot day in 2024
  count as "the record" a 2020 reading is judged against, which reverses
  cause and effect. Instead, each day is compared only to the most extreme
  reading ever seen on that calendar day in a **strictly earlier year**, so
  a new record set in one year correctly moves the bar for every year
  after it, and never for years before it — see the worked spot-check in
  section 3, which finds a real (city, day) example and shows the record
  baseline actually changing over time rather than just asserting it does.
- **"Tied" means ±0.5°F, not ±1°F.** An earlier version of this page used a
  ±1°F band (`diff_f >= -1`) for the "tied" tally category, which is a
  2°F-wide window, not the 1°F-wide "within a degree" that was actually
  intended. `TIED_BAND_F = 0.5` fixes this: "at record (tied)" now means
  `-0.5 <= diff_f <= 0.5`, a 1°F-wide band centered on the record.
- **"Sets a new record" means more than 0.5°F over, not more than 1°F.**
  This threshold should pick up exactly where the tied band leaves off —
  it was briefly left at the old `diff_f > 1` while `TIED_BAND_F` had
  already been tightened to 0.5, which left `diff_f` in `(0.5, 1]`
  classified as neither tied nor record-setting. `classify_diff()` now
  checks `diff_f > TIED_BAND_F` instead of a separately hardcoded 1, so
  the two bands share one boundary with nothing falling between them.
- **Why this color ladder (and why it's not literally the first draft)**:
  it went through a few rounds. The very first version had two buckets
  defined identically ("< 3 days within 3°F" listed twice). The settled
  version is a 9-step **diverging** ladder: two fully-saturated anchor
  colors at the extremes, shading through progressively lighter tones
  toward a neutral gray in the middle, with each of the "tied" / "within
  3°F" / "within 10°F" bands split into its own "3+ days" and "1-2 days"
  tier (checked 3+ first, so a city with 3+ days never gets miscounted into
  the "1-2" tier just because 1-2 is also technically true). One asymmetry
  worth calling out: the bottom tier's label ("At least 1 day within 10°F")
  is a holdover from before the "3+ days within 10°F" tier existed just
  above it — in practice that tier only ever fires for 1-2 days now, since
  3+ is claimed first, but the exact wording wasn't revisited.
- **Daily lows use the same ladder shape with the colors deliberately
  inverted.** For daily highs, red means "notably hot" (close to or beyond
  the record) and blue means "far from the hot record, i.e. a relatively
  cool month." For daily lows, blue instead means "notably cold" (close to
  or beyond the record *low*) and red means "far from the cold record,
  i.e. a relatively mild month" — matching the intuitive association of
  blue with cold and red with warm, at the cost of the two maps not sharing
  one universal color meaning (check each map's own legend).
- **Why 2020 for the multi-year tally**: `{python} TALLY_START_DATE.year`
  was chosen as a round, recent starting point with enough span to show a
  year-over-year pattern rather than just one data point; there's nothing
  special about that year beyond that.
- **`DEBUG_RAISE = False`**: a city that fails at any stage (no usable
  station, insufficient history, stale data, insufficient month coverage,
  or — for the low-temperature analysis specifically — a station that
  reports highs but not lows) is dropped, with the reason logged as an
  HTML comment in the page source, rather than taking down the whole page.
  Flip it to `True` temporarily to get a full traceback while debugging a
  specific city.
- **Meteostat's own per-station-year load failures are logged, not
  printed to the page.** A transient network hiccup fetching one year out
  of a station's multi-decade history is something Meteostat already
  handles gracefully on its own (that year is just dropped; the rest of
  the fetch continues) -- but by default it does so via a stdlib
  `logging.warning(..., exc_info=True)` call that, with no handler
  configured anywhere in this notebook, printed a full traceback straight
  into the rendered page's output. `logging.getLogger("meteostat").setLevel(logging.ERROR)`
  in the setup cell raises Meteostat's own log threshold so that noise
  doesn't surface, without touching this page's own failure reporting
  (`run_stage`/`failures`) below.
- **Large-request guard disabled on purpose**: Meteostat blocks any single
  daily-data request spanning more than 30 years by default. That's turned
  off here (`meteostat.config.block_large_requests = False`) deliberately,
  since computing an honest "record for this calendar day" requires each
  station's *entire* digitized history, not just the last 30 years.
- **`USE_LOCAL_CACHE` must be `False` for any render that actually gets
  published.** With ~250-500 station histories to fetch, re-hitting
  Meteostat on every single test render while iterating on something
  unrelated to the fetch itself (map layout, color choices, and similar)
  was the slowest part of the feedback loop by far. Setting it to `True`
  caches each station's fetch to `cache_dev/` (gitignored, never
  committed) and reuses it on the next render instead of re-fetching —
  but the cache has no concept of "this month's data wasn't available
  yet last time I checked," so it will happily keep serving a stale
  fetch indefinitely. Fine for iterating on this page's code; wrong for
  the render that's meant to reflect an actual month's data.
- **Station fetches run in parallel** (`ThreadPoolExecutor`, up to
  `{python} N_WORKERS` at once) since each is an independent network call to
  Meteostat's bulk data. Every candidate for every city is fetched (not just
  the nearest one, per the station-choice note above), so this stage pulls
  roughly `{python} N_CANDIDATE_STATIONS`x more station histories than there
  are cities — still well worth parallelizing, but it's the long pole in
  this page's render time. `N_WORKERS` was raised from 10 to 16 when the
  city list doubled from 50 to 100, to keep the total render from simply
  doubling too; expect somewhere in the 20-30 minute range for all 100
  cities. That's a real cost, but at a monthly cadence it's a non-issue.
- **Canada and Mexico station coverage is untested territory.** Meteostat
  aggregates station data globally, not just US NOAA/NWS sources, so the
  same `resolve_city` logic (longest history, target-month coverage,
  staleness) is applied to Canadian and Mexican candidates with no special
  casing. Whether those regions have as many long-running, densely-covered
  stations within `STATION_SEARCH_RADIUS_M` as US cities typically do is
  genuinely unknown until a render actually runs — if a Canadian or Mexican
  city is missing from a given month's map, check the HTML source comments
  for why (same `DEBUG_RAISE`/`failures` mechanism as any other city).
- **The main map is deliberately clipped, not a loose "fit everything"
  extent.** `MAIN_EXTENT` is defined as exactly 1° beyond four named
  reference points — north of Edmonton, west of San Francisco, east of
  St. John's NL, south of Puebla ("Pueblo" as given was read as Puebla,
  the only spelling used anywhere else in this file; a literal Pueblo, CO
  reading would cut off all of Mexico, which can't be right given Mexican
  cities were being added in the same request). One real consequence: with
  Puebla itself removed from `CITIES` in this same round, Oaxaca (added at
  the same time, ~17.1°N) now sits just *south* of that clip line and
  won't actually show up on the main map, even though it's still in the
  city list and still fully tallied — a direct side effect of taking the
  clip instruction literally rather than quietly padding it out to fit
  every city that happened to get added alongside it.
- **Alaska and Hawaii get their own insets, positioned inside the map's
  own Pacific Ocean space rather than as a separate outside panel** —
  bottom-left, roughly where the ocean west of Mexico/California actually
  is on this projection. Both are zoomed in tight (Oahu only for Hawaii;
  the Anchorage/Fairbanks corridor for Alaska) and labeled with just the
  state name at the top rather than per-city codes, since there isn't room
  for a recognizable shape *and* readable per-city labels at this size.
  Insets are defined purely by their own geographic extent (a lon/lat
  box), not a hardcoded city list, so both Alaska cities land in the same
  inset automatically. Alaska specifically uses its own Lambert Conformal
  projection centered on Alaska rather than the plain PlateCarree grid —
  PlateCarree visibly stretches high-latitude land east-west (it doesn't
  account for longitude lines converging toward the pole), which was
  making Alaska look wider than it actually is.
- **The legend is back inside the map image, as a horizontal band across
  the bottom.** An earlier version moved it to a separate HTML color-key
  below the image instead, to stop it from competing with the map for
  space — reversed here in favor of a single self-contained image, now
  laid out as `fig.legend(..., loc="lower center", ncol=3)` instead of
  the tall single-column list on the right that a plain matplotlib legend
  defaults to, so it still doesn't eat much vertical room. City-code
  labels are also 1pt larger than the first version of this layout
  (6.5pt, up from 5.5pt) now that there's more room to work with.
- **The bottom tier's label now matches what the code actually checks.**
  It previously read "Not close all month (<3 days within 20°F)," but
  `classify_month()` never actually checks a 20°F band anywhere — that
  tier is reached purely as the fallback once every narrower band above it
  (down to "at least 1 day within 10°F") has failed to match, i.e. zero
  days came within 10°F all month. Relabeled to "No days within 10°F of
  record" (or "...of record low") to say exactly that instead of
  describing a threshold the code doesn't use.
- **Dense clusters of cities can produce overlapping code labels.** Labels
  are placed with a small fixed pixel offset from each point, not by any
  collision-avoidance algorithm — in a tightly-packed region (e.g. the
  Boston-New York-Philadelphia-DC corridor, or the Toronto/Ottawa area),
  some labels may overlap or sit close enough to be hard to read at a
  glance. The underlying `monthly_df` / `monthly_df_min` tables above each
  map list every city's code unambiguously if a label on the map itself is
  unclear.
- **Section 9's climate-zone layer is real Köppen-Geiger classification
  data, not a terrain-shading stand-in.** An earlier version of this page
  used Cartopy's bundled Natural Earth shaded-relief raster
  (`ax.stock_img()`) as a rough visual proxy and was explicit that it
  was *not* a genuine climate classification. That's since been replaced
  with the actual thing: Beck, H.E., N.E. Zimmermann, T.R. McVicar, N.
  Vergopolan, A. Berg, E.F. Wood (2018), "Present and future Köppen-Geiger
  climate classification maps at 1-km resolution," *Scientific Data*
  5:180214, [doi:10.1038/sdata.2018.214](https://doi.org/10.1038/sdata.2018.214),
  CC BY 4.0 — the standard modern reference for this classification, and
  the same one most published Köppen maps (including the one linked when
  this feature was requested) are ultimately built from. Class codes and
  colors are exactly as published in the dataset's own `legend.txt`, not
  invented for this page. The Natural Earth shaded-relief raster is still
  present, but demoted to a muted, low-opacity (20%) grayscale backdrop
  underneath the climate colors (`add_topography_underlay()`), rather than
  the main layer — geographic/topographic context, not the focus.
- **The Köppen data is bundled with the repo, not fetched at render
  time — a deliberate exception to this site's usual practice** (see the
  README, and how every other live-data post here fetches fresh each
  run). The published dataset ships the present-day classification at
  three resolutions; `koppen_na.npz` here is the 5-arcmin ("0p083") grid,
  cropped once (offline, not at render time) to lon -180 to -50 / lat 14
  to 72 and gzip-compressed to **45 KB**. That's a different scale of
  problem than the multi-GB weather-model output other posts on this site
  legitimately fetch fresh each run, and unlike a live external fetch, it
  can't fail or change format out from under a future scheduled render —
  worth it here since the classification itself doesn't change
  month-to-month the way weather does.
- **Alaska and Hawaii's insets show the (approximately) full
  state/territory, not just a tight crop around their cities.** Alaska's
  own extent stops at -180° rather than continuing across the
  antimeridian to the westernmost Aleutian islands, which would need real
  dateline-wraparound handling to render correctly — this still captures
  the mainland, panhandle, and the large majority of the Aleutian chain by
  both area and population. Cartopy's `GeoAxes` never distorts a
  projection's true proportions to force-fit a panel's box shape (it
  letterboxes — adds blank space — instead), so a mismatch between an
  inset's box aspect ratio and its content's true aspect ratio shows up as
  extra margin around the map, not as visible stretching.

## Keeping this page current

Unlike the [tropical cyclone outlook
post](../2026-09-09-ep-storm-precip-wind/index.qmd) (which needs to refresh
daily while a storm is active), this page only needs to refresh once a
month, since it's summarizing a full completed month at a time. It's
rendered on its own **monthly** schedule — see
`.github/workflows/publish.yml` for the actual cron job — separate from
the site's daily/push-triggered rebuild, so it isn't re-fetching ~250
station histories (a 15-20 minute job) on every push to this repo.
