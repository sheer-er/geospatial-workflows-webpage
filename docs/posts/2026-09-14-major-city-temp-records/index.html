Once a month, pulls each of the 50 most populous US cities’ weather station, tallies how many days in the prior calendar month landed near, at, or beyond that station’s all-time high (and separately, all-time low) for the day, and maps both – plus a running multi-year tally since 2020.

What this page does

Every time this page is rendered (once a month — see the note at the bottom), it:

  1. Takes a fixed list of the 50 most populous US cities (a standard proxy for “most influential” — see the caveats section for why population, not some other ranking, was used).
  2. For each city, finds the most complete nearby weather station (the candidate with the longest history and the best coverage of the target month, not just the closest one).
  3. Compares every day of that station’s history against the all-time record for that calendar day — separately for daily highs and daily lows — using an expanding, backward-looking record: a record broken in one year moves the bar for every later year, and never the reverse (see the methodology note and worked example below).
  4. Keeps a running tally since 2020 for both highs and lows, broken out by year.
  5. Focuses on the most recently fully-completed calendar month and, for each city, counts how many days that month landed in each band relative to its record high and its record low — then maps both.
Important

This is a live, self-refreshing page, not a one-time snapshot. There’s no server behind it — it’s a static site. At render time, this code re-fetches real station data and recomputes everything below. What you see is only as fresh as the last render (monthly, via cron — see the bottom of the page).

def classify_diff(diff_f, extreme_label):
    """
    Shared classifier for both daily-high and daily-low comparisons.
    diff_f > 0 always means "this day set a new record in the extreme
    direction" -- expanding_daily_comparison() below flips the sign for
    daily lows so this function never has to know which direction it's
    looking at. extreme_label names that direction for the top bucket,
    e.g. "Above" for highs or "Below" for lows.
    """
    if diff_f > 1:
        return f"{extreme_label} record"
    if -TIED_BAND_F <= diff_f <= TIED_BAND_F:
        return "At record (tied)"
    if diff_f >= -3:
        return "Within 3°F of record"
    return None  # not close enough to tally

def classify_month(counts, tiers):
    """
    counts: dict with days_above, days_tied, days_within_3, days_within_10.
    Checked narrowest/most-extreme condition first at each threshold, so
    "3+ days" and "1-2 days" versions of the same band never both match --
    e.g. days_tied=5 satisfies both ">=3" and ">=1", but since ">=3" is
    checked first, it's the one that wins.
    """
    if counts["days_above"] >= 3:
        return tiers[0]
    if counts["days_above"] >= 1:
        return tiers[1]
    if counts["days_tied"] >= 3:
        return tiers[2]
    if counts["days_tied"] >= 1:
        return tiers[3]
    if counts["days_within_3"] >= 3:
        return tiers[4]
    if counts["days_within_3"] >= 1:
        return tiers[5]
    if counts["days_within_10"] >= 3:
        return tiers[6]
    if counts["days_within_10"] >= 1:
        return tiers[7]
    return tiers[8]

2. Pull each station’s full daily high/low-temperature history

Fetched in parallel — each station’s history is an independent network call, and there’s no reason to wait for one before starting the next. Both the daily high and daily low come back in the same request per station, so adding the low-temperature analysis below didn’t require any extra fetching.

Code 
def fetch_station_daily(station_id):
    ts = meteostat.daily(station_id, HIST_START, FETCH_END, parameters=[Parameter.TMAX, Parameter.TMIN])
    return ts.fetch(units=UnitSystem.IMPERIAL)


# Fetch every candidate for every city (not just the nearest one) so the
# best-populated station can be picked rather than just the closest one
# that clears a minimum bar. This matters: nearby() returns candidates by
# *distance*, and the physically closest site is sometimes a short-lived or
# sparsely-reporting station (e.g. a personal/community site) sitting right
# next to a much longer-running official airport station a few km further
# out. Picking "nearest that passes" over "most complete overall" was
# initially producing "records" built on a couple sparse decades instead of
# a station's full, well-populated history.
all_candidate_ids = sorted({sid for ids in city_candidates.values() for sid in ids})
station_data = {}
with ThreadPoolExecutor(max_workers=N_WORKERS) as pool:
    futures = {pool.submit(fetch_station_daily, sid): sid for sid in all_candidate_ids}
    for future in futures:
        sid = futures[future]
        station_data[sid] = run_stage(f"station {sid} (fetch)", future.result)


MONTH_DATES = pd.date_range(TARGET_MONTH_START, TARGET_MONTH_END, freq="D")


def resolve_city(label, candidates):
    """
    Among this city's already-fetched candidate stations, pick whichever
    has the most actual years of daily-high history (not just whichever is
    nearest), is recent enough, and covers enough of the target month.
    Station choice is driven entirely by the high-temperature series --
    a station reporting both highs and lows normally has matching coverage
    for both, so this avoids running two separate (and possibly
    conflicting) candidate searches. Returns None (city dropped, reason
    logged) if no candidate qualifies.
    """
    reasons = []
    scored = []
    for station_id in candidates:
        df = station_data.get(station_id)
        if df is None or df.empty or "tmax" not in df.columns:
            reasons.append(f"{station_id}: no data returned")
            continue

        tmax_series = df["tmax"].dropna()
        if tmax_series.empty:
            reasons.append(f"{station_id}: no daily-high data returned")
            continue

        n_years = tmax_series.index.year.nunique()
        if n_years < MIN_RECORD_YEARS:
            reasons.append(f"{station_id}: only {n_years} year(s) of history")
            continue

        latest_available = tmax_series.index.max().date()
        if (TARGET_MONTH_END - latest_available).days > MAX_STALENESS_DAYS:
            reasons.append(
                f"{station_id}: most recent reading ({latest_available}) is more "
                f"than {MAX_STALENESS_DAYS} days before month-end {TARGET_MONTH_END}"
            )
            continue

        coverage = tmax_series.index.normalize().isin(MONTH_DATES).sum() / len(MONTH_DATES)
        if coverage < MIN_MONTH_COVERAGE:
            reasons.append(
                f"{station_id}: only {coverage:.0%} of {TARGET_MONTH_START:%B %Y} covered "
                f"(need {MIN_MONTH_COVERAGE:.0%})"
            )
            continue

        tmin_series = df["tmin"].dropna() if "tmin" in df.columns else pd.Series(dtype=float)
        scored.append((n_years, station_id, tmax_series, tmin_series))

    if not scored:
        raise RuntimeError(f"No usable candidate station for {label}: " + "; ".join(reasons))

    # Most years of high-temp history wins, not nearest distance.
    n_years, station_id, tmax_series, tmin_series = max(scored, key=lambda t: t[0])
    return {
        "station": station_id, "n_years": n_years,
        "tmax_series": tmax_series, "tmin_series": tmin_series,
    }

def expanding_daily_comparison(series, mode="max"):
    """
    For one station's full daily series (highs or lows), return a
    DataFrame (one row per date) with each day's reading compared against
    the expanding, backward-looking record for that calendar day -- i.e.
    the most extreme reading ever seen on that month/day in a *strictly
    earlier* year.

    mode="max" is for daily highs (record = highest prior reading);
    mode="min" is for daily lows (record = lowest prior reading, and the
    sign of diff_f is flipped so that diff_f > 0 always means "this day
    set a new record," regardless of mode -- callers never need to know
    which mode produced a given diff_f.

    Rows where fewer than MIN_PRIOR_SAMPLES earlier years exist for that
    calendar day are dropped, not just rows with zero prior years. A
    station can pass the overall MIN_RECORD_YEARS bar and still have a
    calendar day's "record" resting on only a handful of early
    observations -- comparing against a record that immature makes it
    trivially easy to "beat," which would inflate every tally below with
    noise rather than genuine extremes.
    """
    df = series.rename("actual_f").to_frame()
    df["month"] = df.index.month
    df["day"] = df.index.day
    grouped = df.groupby(["month", "day"])["actual_f"]
    df["prior_n"] = grouped.transform(lambda s: s.expanding().count().shift(1))
    if mode == "max":
        df["prior_record_f"] = grouped.transform(lambda s: s.expanding().max().shift(1))
    else:
        df["prior_record_f"] = grouped.transform(lambda s: s.expanding().min().shift(1))
    df = df[df["prior_n"] >= MIN_PRIOR_SAMPLES]
    if mode == "max":
        df["diff_f"] = (df["actual_f"] - df["prior_record_f"]).round(1)
    else:
        df["diff_f"] = (df["prior_record_f"] - df["actual_f"]).round(1)
    return df[["actual_f", "prior_record_f", "diff_f"]]

3. Back-calculated running tally since 2020 — daily highs

A single month is a small sample — most cities aren’t near their record in any given month. To get a real sense of how often major US cities are running hot relative to their own history, this section replays the comparison for every day since datetime.date(2020, 1, 1) through the end of the target month, for each of the 50 resolved cities (using the station histories already pulled above — no extra fetching needed), and keeps a cumulative tally across all of it. The per-day results computed here also feed directly into the monthly map in section 5.

The one thing that has to change for a multi-year replay: “the record” can’t be a fixed number looked up once, because it should only reflect what was actually the record at the time — a day in 2021 should be judged against the record as it stood coming into 2021, not against a hotter day that happened to occur in 2023. So for each station and each calendar day, this uses an expanding, backward-looking record: the highest reading ever seen on that calendar day in any earlier year. If a year sets a new record, that becomes the bar every later year is compared against — and, just as importantly, a year never gets compared against a record set after it.

Method notes & caveats

  • “50 most influential cities” = 50 most populous cities. Population (~2023-2024 Census estimates) is used as a standard, reproducible proxy for “influential” — there’s no single agreed-upon ranking for the latter, and population is the one that’s citable and doesn’t change based on opinion. Dallas/Fort Worth/Arlington originally plotted three overlapping points in one metro area; trimmed to just Dallas. Oakland (already effectively covered by San Francisco/San Jose in the same Bay Area), Long Beach, Fresno, Mesa, and Baltimore were swapped for Billings MT, Boise ID, Sioux Falls SD, New Orleans LA, Salt Lake City UT, Birmingham AL (the most populous of Birmingham/Mobile AL/Jackson MS), and St. Louis MO — trading a few duplicated/nearby metros for broader geographic spread.
  • Data source: Meteostat, which aggregates NOAA/NWS (and other) station daily summaries. Station histories vary in length — some (e.g. long-running first-order airports) go back 80+ years; others considerably less. This is each station’s own digitized daily record, not necessarily an official NWS all-time record for that city (which may rely on a longer or differently-sourced period of record).
  • Why monthly, not daily: a single day is a noisy, low-signal snapshot, and daily reruns mostly re-fetched the same station histories for a one-day-later answer. Rendering once a month for the prior, fully completed month gives station data real time to finalize (some long-running stations lag by a week or more — see the staleness note below) and produces a more meaningful “how hot/cold did this month actually run” summary than a single day ever could.
  • Highs and lows share one mechanism, mirrored. expanding_daily_comparison() takes a mode argument (“max” for daily highs, “min” for daily lows) and internally flips the sign of diff_f for the “min” case, so that diff_f > 0 always means “this day set a new record in the extreme direction” regardless of which one is being computed. classify_diff() and classify_month() are likewise shared by both — only the color/label tables (MONTH_TIERS vs. MONTH_TIERS_MIN) and the category names (“Above record” vs. “Below record”) differ.
  • Station choice picks the most complete candidate, not the nearest one. Up to 5 candidates within 120 km are fetched for each city, and whichever has the most actual years of daily-high history is used — not whichever is physically closest. This was a deliberate fix after an initial version picked the nearest station unconditionally (as long as it cleared MIN_RECORD_YEARS), which for at least one test city turned out to be a nearby short/sparsely-reporting site instead of a much longer-running official airport station a few km further out. The same station (and thus the same daily-low series) is used for both the high-temperature and low-temperature analyses, rather than running two independent searches that could disagree.
  • A candidate station must also cover the target month. Beyond overall history length, MIN_MONTH_COVERAGE (80%) requires a candidate to have data for most of the target month specifically — a station can have decades of history and still have gone offline (or not yet reported) for the one month this page currently cares about.
  • Reporting lag / staleness: some stations’ daily summaries aren’t finalized for a couple of weeks. A candidate is rejected if its most recent reading is more than 21 days behind the target month’s end — generous on purpose, since the long-running official stations that make the best record sources also tend to have the slowest final QC lag.
  • A calendar day’s record also needs a minimum sample size of its own (MIN_PRIOR_SAMPLES = 15 earlier years). A station can pass the overall history-length bar while a specific month/day within it still has very few prior observations early in the record, making that day’s “record” trivially easy to beat — this floor keeps those thin spots out of every tally on this page.
  • The multi-year tallies and monthly maps use an expanding, backward-looking record. Comparing every day against the extreme over all years, including ones after it, would let e.g. a hot day in 2024 count as “the record” a 2020 reading is judged against, which reverses cause and effect. Instead, each day is compared only to the most extreme reading ever seen on that calendar day in a strictly earlier year, so a new record set in one year correctly moves the bar for every year after it, and never for years before it — see the worked spot-check in section 3, which finds a real (city, day) example and shows the record baseline actually changing over time rather than just asserting it does.
  • “Tied” means ±0.5°F, not ±1°F. An earlier version of this page used a ±1°F band (diff_f >= -1) for the “tied” tally category, which is a 2°F-wide window, not the 1°F-wide “within a degree” that was actually intended. TIED_BAND_F = 0.5 fixes this: “at record (tied)” now means -0.5 <= diff_f <= 0.5, a 1°F-wide band centered on the record.
  • Why this color ladder (and why it’s not literally the first draft): it went through a few rounds. The very first version had two buckets defined identically (“< 3 days within 3°F” listed twice). The settled version is a 9-step diverging ladder: two fully-saturated anchor colors at the extremes, shading through progressively lighter tones toward a neutral gray in the middle, with each of the “tied” / “within 3°F” / “within 10°F” bands split into its own “3+ days” and “1-2 days” tier (checked 3+ first, so a city with 3+ days never gets miscounted into the “1-2” tier just because 1-2 is also technically true). One asymmetry worth calling out: the bottom tier’s label (“At least 1 day within 10°F”) is a holdover from before the “3+ days within 10°F” tier existed just above it — in practice that tier only ever fires for 1-2 days now, since 3+ is claimed first, but the exact wording wasn’t revisited.
  • Daily lows use the same ladder shape with the colors deliberately inverted. For daily highs, red means “notably hot” (close to or beyond the record) and blue means “far from the hot record, i.e. a relatively cool month.” For daily lows, blue instead means “notably cold” (close to or beyond the record low) and red means “far from the cold record, i.e. a relatively mild month” — matching the intuitive association of blue with cold and red with warm, at the cost of the two maps not sharing one universal color meaning (check each map’s own legend).
  • Why 2020 for the multi-year tally: 2020 was chosen as a round, recent starting point with enough span to show a year-over-year pattern rather than just one data point; there’s nothing special about that year beyond that.
  • DEBUG_RAISE = False: a city that fails at any stage (no usable station, insufficient history, stale data, insufficient month coverage, or — for the low-temperature analysis specifically — a station that reports highs but not lows) is dropped, with the reason logged as an HTML comment in the page source, rather than taking down the whole page. Flip it to True temporarily to get a full traceback while debugging a specific city.
  • Large-request guard disabled on purpose: Meteostat blocks any single daily-data request spanning more than 30 years by default. That’s turned off here (meteostat.config.block_large_requests = False) deliberately, since computing an honest “record for this calendar day” requires each station’s entire digitized history, not just the last 30 years.
  • Station fetches run in parallel (ThreadPoolExecutor, up to 10 at once) since each is an independent network call to Meteostat’s bulk data. Every candidate for every city is fetched (not just the nearest one, per the station-choice note above), so this stage pulls roughly 5x more station histories than there are cities — still well worth parallelizing, but it’s the long pole in this page’s render time (on the order of 15-20 minutes for all 50 cities). That’s a real cost, but at a monthly cadence it’s a non-issue.

Keeping this page current

Unlike the tropical cyclone outlook post (which needs to refresh daily while a storm is active), this page only needs to refresh once a month, since it’s summarizing a full completed month at a time. It’s rendered on its own monthly schedule — see .github/workflows/publish.yml for the actual cron job — separate from the site’s daily/push-triggered rebuild, so it isn’t re-fetching ~250 station histories (a 15-20 minute job) on every push to this repo.

## What this page does

Every time this page is rendered (once a month — see the note at the
bottom), it:

1. Takes a fixed list of the **50 most populous US cities** (a standard proxy
   for "most influential" — see the caveats section for why population,
   not some other ranking, was used).
2. For each city, finds the **most complete nearby weather station** (the
   candidate with the longest history and the best coverage of the target
   month, not just the closest one).
3. Compares **every day of that station's history** against the all-time
   record for that calendar day — separately for **daily highs** and
   **daily lows** — using an **expanding, backward-looking record**: a
   record broken in one year moves the bar for every later year, and never
   the reverse (see the methodology note and worked example below).
4. Keeps a **running tally since 2020** for both highs and lows, broken out
   by year.
5. Focuses on the **most recently fully-completed calendar month** and, for
   each city, counts how many days that month landed in each band relative
   to its record high and its record low — then maps both.

::: {.callout-important}
**This is a live, self-refreshing page, not a one-time snapshot.** There's
no server behind it — it's a static site. At render time, this code
re-fetches real station data and recomputes everything below. What you see
is only as fresh as the last render (monthly, via cron — see the bottom of
the page).

```{python}
def classify_month(counts, tiers):
    """
    counts: dict with days_above, days_tied, days_within_3, days_within_10.
    Checked narrowest/most-extreme condition first at each threshold, so
    "3+ days" and "1-2 days" versions of the same band never both match --
    e.g. days_tied=5 satisfies both ">=3" and ">=1", but since ">=3" is
    checked first, it's the one that wins.
    """
    if counts["days_above"] >= 3:
        return tiers[0]
    if counts["days_above"] >= 1:
        return tiers[1]
    if counts["days_tied"] >= 3:
        return tiers[2]
    if counts["days_tied"] >= 1:
        return tiers[3]
    if counts["days_within_3"] >= 3:
        return tiers[4]
    if counts["days_within_3"] >= 1:
        return tiers[5]
    if counts["days_within_10"] >= 3:
        return tiers[6]
    if counts["days_within_10"] >= 1:
        return tiers[7]
    return tiers[8]
```

## 2. Pull each station's full daily high/low-temperature history

Fetched in parallel — each station's history is an independent network call,
and there's no reason to wait for one before starting the next. Both the
daily high and daily low come back in the same request per station, so
adding the low-temperature analysis below didn't require any extra fetching.

```{python}
#| label: fetch-histories

def fetch_station_daily(station_id):
    ts = meteostat.daily(station_id, HIST_START, FETCH_END, parameters=[Parameter.TMAX, Parameter.TMIN])

# Fetch every candidate for every city (not just the nearest one) so the
# best-populated station can be picked rather than just the closest one
# that clears a minimum bar. This matters: nearby() returns candidates by
# *distance*, and the physically closest site is sometimes a short-lived or
# sparsely-reporting station (e.g. a personal/community site) sitting right
# next to a much longer-running official airport station a few km further
# out. Picking "nearest that passes" over "most complete overall" was
# initially producing "records" built on a couple sparse decades instead of
# a station's full, well-populated history.
all_candidate_ids = sorted({sid for ids in city_candidates.values() for sid in ids})
station_data = {}
with ThreadPoolExecutor(max_workers=N_WORKERS) as pool:
    futures = {pool.submit(fetch_station_daily, sid): sid for sid in all_candidate_ids}
    for future in futures:
        sid = futures[future]
        station_data[sid] = run_stage(f"station {sid} (fetch)", future.result)


MONTH_DATES = pd.date_range(TARGET_MONTH_START, TARGET_MONTH_END, freq="D")


def resolve_city(label, candidates):
    """
    Among this city's already-fetched candidate stations, pick whichever
    has the most actual years of daily-high history (not just whichever is
    nearest), is recent enough, and covers enough of the target month.
    Station choice is driven entirely by the high-temperature series --
    a station reporting both highs and lows normally has matching coverage
    for both, so this avoids running two separate (and possibly
    conflicting) candidate searches. Returns None (city dropped, reason
    logged) if no candidate qualifies.
    """
    reasons = []
    scored = []
    for station_id in candidates:
        df = station_data.get(station_id)
        if df is None or df.empty or "tmax" not in df.columns:
            reasons.append(f"{station_id}: no data returned")
            continue

        tmax_series = df["tmax"].dropna()
        if tmax_series.empty:
            reasons.append(f"{station_id}: no daily-high data returned")
            continue

        n_years = tmax_series.index.year.nunique()
        if n_years < MIN_RECORD_YEARS:
            reasons.append(f"{station_id}: only {n_years} year(s) of history")
            continue

        latest_available = tmax_series.index.max().date()
        if (TARGET_MONTH_END - latest_available).days > MAX_STALENESS_DAYS:
            reasons.append(
                f"{station_id}: most recent reading ({latest_available}) is more "
                f"than {MAX_STALENESS_DAYS} days before month-end {TARGET_MONTH_END}"
            )
            continue

        coverage = tmax_series.index.normalize().isin(MONTH_DATES).sum() / len(MONTH_DATES)
        if coverage < MIN_MONTH_COVERAGE:
            reasons.append(
                f"{station_id}: only {coverage:.0%} of {TARGET_MONTH_START:%B %Y} covered "
                f"(need {MIN_MONTH_COVERAGE:.0%})"
            )
            continue

        tmin_series = df["tmin"].dropna() if "tmin" in df.columns else pd.Series(dtype=float)
        scored.append((n_years, station_id, tmax_series, tmin_series))

    if not scored:
        raise RuntimeError(f"No usable candidate station for {label}: " + "; ".join(reasons))

    # Most years of high-temp history wins, not nearest distance.
    n_years, station_id, tmax_series, tmin_series = max(scored, key=lambda t: t[0])
    return {
        "station": station_id, "n_years": n_years,
        "tmax_series": tmax_series, "tmin_series": tmin_series,
    }


results = {}

    futures = {
        pool.submit(resolve_city, label, city_candidates[label]): label

        for label in [f"{name}, {state}"]
    }
```

```{python}
#| label: expanding-comparison-fn
#| output: false

def expanding_daily_comparison(series, mode="max"):
    """
    For one station's full daily series (highs or lows), return a
    DataFrame (one row per date) with each day's reading compared against
    the expanding, backward-looking record for that calendar day -- i.e.
    the most extreme reading ever seen on that month/day in a *strictly
    earlier* year.

    mode="max" is for daily highs (record = highest prior reading);
    mode="min" is for daily lows (record = lowest prior reading, and the
    sign of diff_f is flipped so that diff_f > 0 always means "this day
    set a new record," regardless of mode -- callers never need to know
    which mode produced a given diff_f.

    Rows where fewer than MIN_PRIOR_SAMPLES earlier years exist for that
    calendar day are dropped, not just rows with zero prior years. A
    station can pass the overall MIN_RECORD_YEARS bar and still have a
    calendar day's "record" resting on only a handful of early
    observations -- comparing against a record that immature makes it
    trivially easy to "beat," which would inflate every tally below with
    noise rather than genuine extremes.
    """
    df = series.rename("actual_f").to_frame()
    df["month"] = df.index.month
    df["day"] = df.index.day
    grouped = df.groupby(["month", "day"])["actual_f"]
    df["prior_n"] = grouped.transform(lambda s: s.expanding().count().shift(1))
    if mode == "max":
        df["prior_record_f"] = grouped.transform(lambda s: s.expanding().max().shift(1))
    else:
        df["prior_record_f"] = grouped.transform(lambda s: s.expanding().min().shift(1))
    df = df[df["prior_n"] >= MIN_PRIOR_SAMPLES]
    if mode == "max":
        df["diff_f"] = (df["actual_f"] - df["prior_record_f"]).round(1)
    else:
        df["diff_f"] = (df["prior_record_f"] - df["actual_f"]).round(1)
    return df[["actual_f", "prior_record_f", "diff_f"]]
```

## 3. Back-calculated running tally since 2020 — daily highs

A single month is a small sample — most cities aren't near their record in
any given month. To get a real sense of *how often* major US cities are
running hot relative to their own history, this section replays the
comparison for **every day since `{python} TALLY_START_DATE`** through the
end of the target month, for each of the `{python} len(results)` resolved
cities (using the station histories already pulled above — no extra
fetching needed), and keeps a cumulative tally across all of it. The
per-day results computed here also feed directly into the monthly map in
section 5.

The one thing that has to change for a multi-year replay: "the record"
can't be a fixed number looked up once, because it should only reflect what
was *actually the record at the time* — a day in 2021 should be judged
against the record as it stood coming into 2021, not against a hotter day
that happened to occur in 2023. So for each station and each calendar day,
this uses an **expanding, backward-looking record**: the highest reading
ever seen on that calendar day in any *earlier* year. If a year sets a new
record, that becomes the bar every later year is compared against — and,
just as importantly, a year *never* gets compared against a record set
after it.

```{python}
#| label: historical-tally

daily_frames = []

                            lambda r=r: expanding_daily_comparison(r["tmax_series"], mode="max"))
    if comparison is None:
        continue
    comparison = comparison.loc[TALLY_START_TS:TARGET_MONTH_END_TS].copy()
    comparison["City"] = label
    daily_frames.append(comparison)

)
```

## Method notes & caveats

- **"50 most influential cities" = 50 most populous cities.** Population
  (~2023-2024 Census estimates) is used as a standard, reproducible proxy
  for "influential" — there's no single agreed-upon ranking for the latter,
  and population is the one that's citable and doesn't change based on
  opinion. Dallas/Fort Worth/Arlington originally plotted three overlapping
  points in one metro area; trimmed to just Dallas. Oakland (already
  effectively covered by San Francisco/San Jose in the same Bay Area), Long
  Beach, Fresno, Mesa, and Baltimore were swapped for Billings MT, Boise ID,
  Sioux Falls SD, New Orleans LA, Salt Lake City UT, Birmingham AL (the most
  populous of Birmingham/Mobile AL/Jackson MS), and St. Louis MO — trading a
  few duplicated/nearby metros for broader geographic spread.
- **Data source**: [Meteostat](https://meteostat.net/), which aggregates
  NOAA/NWS (and other) station daily summaries. Station histories vary in
  length — some (e.g. long-running first-order airports) go back 80+ years;
  others considerably less. This is each **station's own digitized daily
  record**, not necessarily an official NWS all-time record for that city
  (which may rely on a longer or differently-sourced period of record).
- **Why monthly, not daily**: a single day is a noisy, low-signal snapshot,
  and daily reruns mostly re-fetched the same station histories for a
  one-day-later answer. Rendering once a month for the *prior, fully
  completed* month gives station data real time to finalize (some
  long-running stations lag by a week or more — see the staleness note
  below) and produces a more meaningful "how hot/cold did this month
  actually run" summary than a single day ever could.
- **Highs and lows share one mechanism, mirrored.** `expanding_daily_comparison()`
  takes a `mode` argument ("max" for daily highs, "min" for daily lows) and
  internally flips the sign of `diff_f` for the "min" case, so that
  `diff_f > 0` always means "this day set a new record in the extreme
  direction" regardless of which one is being computed. `classify_diff()`
  and `classify_month()` are likewise shared by both — only the color/label
  tables (`MONTH_TIERS` vs. `MONTH_TIERS_MIN`) and the category names
  ("Above record" vs. "Below record") differ.
- **Station choice picks the most complete candidate, not the nearest one.**
  Up to `{python} N_CANDIDATE_STATIONS` candidates within
  `{python} STATION_SEARCH_RADIUS_M // 1000` km are fetched for each city,
  and whichever has the most actual years of daily-high history is used —
  *not* whichever is physically closest. This was a deliberate fix after an
  initial version picked the nearest station unconditionally (as long as it
  cleared `MIN_RECORD_YEARS`), which for at least one test city turned out
  to be a nearby short/sparsely-reporting site instead of a much
  longer-running official airport station a few km further out. The same
  station (and thus the same daily-low series) is used for both the
  high-temperature and low-temperature analyses, rather than running two
  independent searches that could disagree.
- **A candidate station must also cover the target month.** Beyond overall
  history length, `MIN_MONTH_COVERAGE` (`{python} f"{MIN_MONTH_COVERAGE:.0%}"`)
  requires a candidate to have data for most of the target month specifically
  — a station can have decades of history and still have gone offline (or
  not yet reported) for the one month this page currently cares about.
- **Reporting lag / staleness**: some stations' daily summaries aren't
  finalized for a couple of weeks. A candidate is rejected if its most
  recent reading is more than `{python} MAX_STALENESS_DAYS` days behind the
  target month's end — generous on purpose, since the long-running official
  stations that make the best *record* sources also tend to have the
  slowest final QC lag.
- **A calendar day's record also needs a minimum sample size of its own**
  (`MIN_PRIOR_SAMPLES` = `{python} MIN_PRIOR_SAMPLES` earlier years). A
  station can pass the overall history-length bar while a specific
  month/day within it still has very few prior observations early in the
  record, making that day's "record" trivially easy to beat — this floor
  keeps those thin spots out of every tally on this page.
- **The multi-year tallies and monthly maps use an *expanding*,
  backward-looking record.** Comparing every day against the extreme over
  *all* years, including ones after it, would let e.g. a hot day in 2024
  count as "the record" a 2020 reading is judged against, which reverses
  cause and effect. Instead, each day is compared only to the most extreme
  reading ever seen on that calendar day in a **strictly earlier year**, so
  a new record set in one year correctly moves the bar for every year
  after it, and never for years before it — see the worked spot-check in
  section 3, which finds a real (city, day) example and shows the record
  baseline actually changing over time rather than just asserting it does.
- **"Tied" means ±0.5°F, not ±1°F.** An earlier version of this page used a
  ±1°F band (`diff_f >= -1`) for the "tied" tally category, which is a
  2°F-wide window, not the 1°F-wide "within a degree" that was actually
  intended. `TIED_BAND_F = 0.5` fixes this: "at record (tied)" now means
  `-0.5 <= diff_f <= 0.5`, a 1°F-wide band centered on the record.
- **Why this color ladder (and why it's not literally the first draft)**:
  it went through a few rounds. The very first version had two buckets
  defined identically ("< 3 days within 3°F" listed twice). The settled
  version is a 9-step **diverging** ladder: two fully-saturated anchor
  colors at the extremes, shading through progressively lighter tones
  toward a neutral gray in the middle, with each of the "tied" / "within
  3°F" / "within 10°F" bands split into its own "3+ days" and "1-2 days"
  tier (checked 3+ first, so a city with 3+ days never gets miscounted into
  the "1-2" tier just because 1-2 is also technically true). One asymmetry
  worth calling out: the bottom tier's label ("At least 1 day within 10°F")
  is a holdover from before the "3+ days within 10°F" tier existed just
  above it — in practice that tier only ever fires for 1-2 days now, since
  3+ is claimed first, but the exact wording wasn't revisited.
- **Daily lows use the same ladder shape with the colors deliberately
  inverted.** For daily highs, red means "notably hot" (close to or beyond
  the record) and blue means "far from the hot record, i.e. a relatively
  cool month." For daily lows, blue instead means "notably cold" (close to
  or beyond the record *low*) and red means "far from the cold record,
  i.e. a relatively mild month" — matching the intuitive association of
  blue with cold and red with warm, at the cost of the two maps not sharing
  one universal color meaning (check each map's own legend).
- **Why 2020 for the multi-year tally**: `{python} TALLY_START_DATE.year`
  was chosen as a round, recent starting point with enough span to show a
  year-over-year pattern rather than just one data point; there's nothing
  special about that year beyond that.
- **`DEBUG_RAISE = False`**: a city that fails at any stage (no usable
  station, insufficient history, stale data, insufficient month coverage,
  or — for the low-temperature analysis specifically — a station that
  reports highs but not lows) is dropped, with the reason logged as an
  HTML comment in the page source, rather than taking down the whole page.
  Flip it to `True` temporarily to get a full traceback while debugging a
  specific city.
- **Large-request guard disabled on purpose**: Meteostat blocks any single
  daily-data request spanning more than 30 years by default. That's turned
  off here (`meteostat.config.block_large_requests = False`) deliberately,
  since computing an honest "record for this calendar day" requires each
  station's *entire* digitized history, not just the last 30 years.
- **Station fetches run in parallel** (`ThreadPoolExecutor`, up to
  `{python} N_WORKERS` at once) since each is an independent network call to
  Meteostat's bulk data. Every candidate for every city is fetched (not just
  the nearest one, per the station-choice note above), so this stage pulls
  roughly `{python} N_CANDIDATE_STATIONS`x more station histories than there
  are cities — still well worth parallelizing, but it's the long pole in
  this page's render time (on the order of 15-20 minutes for all 50
  cities). That's a real cost, but at a monthly cadence it's a non-issue.
